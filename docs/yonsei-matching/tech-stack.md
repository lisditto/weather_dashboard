# 기술 스택 제안 & 근거

**전제:** 1인(비개발자) 창업자, Vercel 호스팅, 토스 결제, 직접 클릭 테스트.
→ 설계 원칙은 단 세 가지입니다.

1. **부품 수를 최소화한다** — 관리할 계정·대시보드·청구서가 적을수록 좋다.
2. **눈으로 확인 가능한 것을 고른다** — 시각적 대시보드가 있어 클릭으로 검증된다.
3. **전부 관리형(매니지드)으로** — 직접 서버를 돌리거나 운영하지 않는다.

## TL;DR — 추천 스택

| 레이어 | 선택 | 한 줄 이유 |
|---|---|---|
| 언어 | **TypeScript** | 40문항·매칭·결제의 실수를 타입이 잡아줌 (코드는 AI가 작성) |
| 앱 프레임워크 | **Next.js (App Router)** | 랜딩 + 설문 + 백엔드 API를 한 덩어리로. Vercel과 한 몸 |
| 화면(UI) | **Tailwind CSS + shadcn/ui** | 와이어프레임의 카드·토글·진행바를 빠르고 깔끔하게 |
| 설문 폼 | **React Hook Form + Zod** | 다단계·자동저장·검증에 최적 |
| DB + 인증 | **Supabase** (Postgres + Auth) | DB와 회원관리를 한 서비스로. **표·유저를 화면에서 눈으로 확인** |
| 이메일 | **Resend + React Email** | 인증코드·매칭결과·가이드 메일. 보낸 메일을 대시보드에서 확인 |
| 결제 | **TossPayments** | 카카오페이·토스·카드·가상계좌 + **자동결제(빌링)** 지원 |
| 정기 작업 | **Vercel Cron** | "매주 월요일" 매칭 배치를 한 줄 설정으로 |
| 남용 방지 | **Upstash Redis** | 인증코드 무한 재전송 같은 악용 차단 |
| 나중에 | Sentry(오류알림) · PostHog(지표) | 출시 후 추가. 초기엔 생략 가능 |

> **관리할 계정은 사실상 5개**입니다: GitHub · Vercel · Supabase · Resend ·
> TossPayments. 모두 웹 대시보드가 있어 비개발자도 눈으로 상태를 확인할 수 있습니다.

## 레이어별 선택 & 근거

### 앱: Next.js + TypeScript on Vercel
- 랜딩 페이지(검색 노출 중요)·설문(폼 중심)·백엔드 로직을 **하나의 프로젝트**로
  처리 → 1인 개발에 최적. 언어도 하나(TypeScript)라 머릿속 전환 비용이 없습니다.
- Vercel과 가장 궁합이 좋아 **코드를 올리면 자동으로 배포**되고, 기능마다
  미리보기(Preview) URL이 생겨 **바로 눌러볼 수 있습니다.**

### 화면: Tailwind + shadcn/ui
- 와이어프레임에 반복적으로 등장하는 카드·진행바·토글·다이얼로그·폼을
  **접근성까지 보장된 기성 부품**으로 빠르게 조립. 디자인 일관성도 자동 확보.

### 데이터 + 회원: Supabase
- **표(테이블) 편집기**가 있어 "누가 가입했지?", "설문 응답이 들어왔나?"를
  **코드 없이 화면에서 클릭으로 확인**할 수 있습니다 → 비개발자에게 결정적 장점.
- 회원가입/로그인/이메일 인증/비밀번호 찾기를 DB와 **한 서비스 안에서** 해결 →
  부품 수 감소. `@yonsei.ac.kr` 한정과 6자리 코드 같은 맞춤 로직은 제가 처리합니다.
- 리전은 **서울 또는 도쿄**로 설정(아래 리스크 ④).

### 이메일: Resend + React Email
- 이 서비스에서 이메일은 **부가기능이 아니라 핵심 기능**입니다(인증·매칭통보·
  가이드·영수증, 그리고 "이메일로만 소통"). Resend는 React로 예쁜 메일을 만들고,
  **보낸 메일·도달 여부를 대시보드에서 눈으로 확인**할 수 있어 적합합니다.
- 단, 한국 도달률 이슈가 있어 대비가 필요(리스크 ②).

### 결제: TossPayments
- 와이어프레임이 요구하는 **카카오페이·토스페이·카드·무통장입금**을 모두 커버하고,
  멤버십 **자동청구(빌링키)**를 지원합니다.
- **개발·테스트는 토스의 "테스트 키"로 계약 없이 전부 가능**합니다. 실제 돈을 받는
  시점에만 사업자등록 + 정식 계약이 필요합니다(리스크 ① 참고).

### 정기 매칭: Vercel Cron
- "매주 월요일 오후 5시"에 매칭 알고리즘을 돌리고 결과 메일을 보내는 작업을
  Vercel 설정 한 줄로 예약. 별도 서버가 필요 없습니다.
- 테스트 편의를 위해 **"지금 매칭 실행" 버튼**을 관리자용으로 함께 만들어,
  일주일을 기다리지 않고도 눌러서 확인할 수 있게 합니다.

## 한국 특화 핵심 리스크 4가지

여기서 스택의 성패가 갈립니다. 글로벌 기본값을 그대로 쓰면 한국에서 깨집니다.

### ① 결제 — 국내 PG(토스)가 맞고, Stripe는 부적합
- 와이어프레임이 카카오페이·무통장입금을 명시 → 글로벌 결제사(Stripe)는 국내
  간편결제·카드 정산·가상계좌를 제대로 못 다룹니다. **토스 선택은 정답입니다.**
- **현실 절차:** 실제 결제를 받으려면 **개인사업자 등록 + 토스 정식 계약/심사**가
  필요합니다. 다행히 **개발·테스트는 테스트 키로 선행** 가능하니, 만드는 동안
  사업자 등록을 병행하면 됩니다.
- 💰 **주 단위 자동청구 주의:** 1,900원을 매주 결제하면 건당 카드 수수료(대략
  결제액의 수 %)가 수익을 크게 깎습니다. **월 단위로 묶어 청구**(매칭은 주 1회
  유지)하는 편이 수수료 손실이 훨씬 적습니다. 강력히 권장.

### ② 이메일 도달률 — 사업 리스크
- 이메일이 핵심 채널이라 **스팸함 직행 = 서비스 실패**입니다. Resend/SendGrid 같은
  글로벌 발신은 **네이버·다음(카카오) 수신함에서 차단·스팸 처리되는 사례**가 흔합니다.
- **대비책:** 발신 도메인에 SPF/DKIM/DMARC 정식 설정 + 발신 평판 워밍업, 네이버/
  다음 도달 모니터링, 필요 시 국내 친화 발송 경로(예: AWS SES 서울)를 백업으로.
- 다행히 수신측이 `@yonsei.ac.kr`(대개 Google Workspace/MS)이라 상대적으로 양호합니다.

### ③ 개인정보보호법(PIPA) — 협상 불가
- 연애관·성향 같은 **민감 정보를 다루는 데이팅 서비스**입니다. 법적으로:
  - 개인정보처리방침 게시, **수집·이용 동의** 분리 수집, 목적 제한, 보유·파기 정책
  - 비밀번호 안전 해싱, 민감 설문응답 저장 시 암호화 검토
- 제품의 "이름·연락처 비공개, 이메일만 소통" 설계는 PIPA의 **최소수집 원칙과 잘
  맞습니다** → 처음부터 **PII(개인식별정보)를 최소·분리**하도록 DB를 설계합니다.

### ④ 데이터 리전/지연
- 사용자가 전부 국내이므로 Supabase 리전과 Vercel 함수 리전을 **서울/도쿄
  (icn1/hnd1)**로 고정. 기본값(미국)으로 두면 모든 화면이 체감상 느려집니다.

## 채택하지 않은 것 (의도적 제외)

- **Streamlit (현재 repo 스택)** — 내부 데이터 대시보드 도구라, 인증·결제·검색노출·
  이메일 플로우가 필요한 **공개 소비자 제품에는 부적합**합니다.
- **Stripe** — 국내 결제수단 미흡(리스크 ①).
- **실시간 채팅 인프라(WebSocket 등)** — 제품이 의도적으로 "이메일 소통"이라
  **불필요**. 덕분에 스택이 크게 단순해집니다.
- **무거운 자동화 테스트 강제** — 창업자가 클릭으로 검증하는 워크플로에 맞춰,
  단계별 **수동 확인 체크리스트** 중심으로 갑니다(핵심 플로우만 추후 자동화 고려).

## 운영 비용 개략 (초기)

- Vercel · Supabase · Resend · Upstash 모두 **무료 티어로 시작 가능**. 사용자가
  늘면 단계적으로 유료 전환(보통 월 $20~25 수준부터).
- 토스 결제 **수수료**(결제액의 수 %)는 매출 발생 시에만. → 주 단위보다 월 단위
  청구가 수수료 효율이 좋은 이유.
- 도메인 비용 연 1~2만원대.
